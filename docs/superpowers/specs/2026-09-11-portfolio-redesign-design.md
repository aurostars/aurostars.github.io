# 个人主页重构设计规范

日期：2026-09-11  
状态：已确认，等待书面审阅  
目标仓库：`aurostars/aurostars.github.io`

## 1. 项目目标

将当前个人主页从暗色玻璃拟态的简历式页面，重构为面向 AI 产品经理招聘者的明亮型案例作品集。

新版主页需要让招聘者在短时间内完成三个判断：

1. 董星专注于 AI 产品设计与产品落地。
2. 董星能够独立完成从问题定义、工作流设计到可用产品交付的完整过程。
3. 页面中的能力判断有真实项目、真实界面和可点击仓库作为证据。

## 2. 已确认的设计边界

- 完全抛开现有暗色玻璃拟态视觉，从零建立新视觉语言。
- 优先服务 AI 产品经理岗位招聘者。
- 页面保持明亮、通透、有高级感，不采用压抑的深色主题。
- 不使用个人照片。
- 大胆精简现有简历内容，案例是页面主体。
- 实习经历每段只显示一行。
- 联系区域只包含邮箱和 GitHub。
- 所有案例均为 GitHub 个人项目。
- 排除 `vedio-for-jiji` 与 `aurostars.github.io`。
- 不虚构个人经历、项目数据、在线服务、产品界面或用户成果。

## 3. 目标受众与成功标准

### 3.1 首要受众

正在招聘 AI 产品经理的招聘者、业务负责人和产品负责人。

### 3.2 成功标准

- 首屏能够清晰表达 AI 产品经理定位与核心价值。
- 招聘者在 30 秒内能够发现并打开代表案例。
- 四个项目均包含背景与目标、工作流程、真实图片和可点击链接。
- 案例描述突出产品问题、关键判断和完整流程，不堆叠技术名词。
- 实习经历完整保留，但不抢占案例的视觉权重。
- 桌面端、平板端和手机端均可顺畅阅读和操作。
- 页面满足键盘访问、焦点可见、语义结构和 WCAG AA 对比度要求。
- GitHub Pages 静态导出、资源路径和部署流程保持可用。

## 4. 设计方向

### 4.1 视觉主题

方向名称：Product Storyboard

设计参数：

- `DESIGN_VARIANCE: 7`
- `MOTION_INTENSITY: 6`
- `VISUAL_DENSITY: 4`

视觉语言：

- 冷白主背景。
- 银灰用于层次与辅助表面。
- 钴蓝作为全页唯一强调色。
- 深石墨色用于正文，不使用纯黑。
- 页面全程保持同一明亮主题，不插入突兀的深色区块。
- 采用现代无衬线字体。标题紧凑有力度，正文轻盈易读。
- 不使用 AI 紫色渐变、外发光、通用玻璃卡片或三列等宽卡片。

### 4.2 圆角与表面

- 图片和案例容器统一使用 16px 圆角。
- 按钮统一使用 10px 圆角。
- 只有真实层级关系需要容器，普通内容优先使用留白和分隔。
- 阴影必须与冷灰背景同色相，并保持轻量。

### 4.3 图片原则

- 每个案例至少包含一张真实产品主图。
- 复杂案例增加 2-3 张关键功能或工作流程截图。
- 截图使用统一的产品展示框，不在图片上叠加装饰标签。
- 不使用随机图库照片、真人照片、手绘假界面或由空白矩形拼成的假截图。
- 仓库已有截图时直接使用原始资产。
- 仓库没有截图时，在实现阶段运行真实应用并截取真实界面。
- 若项目无法运行且没有真实截图，则使用项目标识、代码结构或流程图作为替代，并明确说明，不伪造界面。

## 5. 信息架构

页面由六个主要区域组成。

### 5.1 导航

桌面导航单行展示：

- 董星
- 案例
- 经历
- 联系

导航高度不超过 72px。移动端使用简洁菜单，不复制一套冗余导航内容。

### 5.2 Hero

Hero 使用不对称布局。

左侧内容：

- 身份：AI 产品经理
- 标题：从问题定义，到结果验证
- 简短说明：强调将 AI 能力接入真实工作流，并通过产品和数据持续验证价值
- 主按钮：查看案例

右侧内容：

- 使用四个真实项目的界面截图组成产品视觉拼贴
- 不使用个人照片
- 不使用抽象渐变球、装饰性 3D 对象或虚构产品界面

Hero 约束：

- 标题桌面端不超过两行。
- 说明不超过 20 个中文词组的等效长度。
- 主按钮首屏可见。
- 使用 `min-height: 100dvh`，不使用 `height: 100vh`。

### 5.3 案例区域

案例是页面主体，占页面内容约 65%。

排序已确认：

1. 秋招网申助手
2. 面试复盘助手
3. 智能简历编辑工具
4. 智能会议纪要工具

首个案例拥有最大视觉面积，后续案例使用不同版式。禁止四个相同卡片连续排列，也禁止三段以上连续左右交替图文。

每个案例统一包含：

1. 项目名称和一句话定位
2. 项目背景与目标
3. 核心用户问题
4. 五步工作流程
5. 核心功能或产品判断
6. 真实产品图片
7. 可验证的项目数据
8. GitHub、Release 或在线体验链接
9. 项目来源与个人贡献说明

#### 案例一：秋招网申助手

仓库：<https://github.com/aurostars/Job-Application-Helper>

背景与目标：减少网申中的重复录入、多简历切换、复杂字段识别和投递记录分散问题。

工作流程：

1. 导入并结构化简历资料。
2. 在招聘页面识别或框选目标表单区域。
3. 结合截图、DOM 元数据与个人资料进行字段匹配。
4. 将已验证内容写入表单并允许人工调整。
5. 保存投递记录并通过 WebDAV 安全同步。

可验证亮点：

- 浏览器扩展形态。
- 支持多简历资料。
- 视觉与文本联合的 AI 表单匹配。
- 投递记录管理。
- WebDAV 冲突防护同步。
- Releases 页面可点击访问。

真实资产：

- `public/icons/job-application-autofill-icon.svg`
- `public/icons/icon128.png`
- 实现阶段运行真实扩展并补充表单识别、侧边栏和投递记录截图。

#### 案例二：面试复盘助手

仓库：<https://github.com/aurostars/Interview-Review-Assistant>

背景与目标：解决面试后细节遗忘、评价主观、改进方向不清晰和多场面试难以横向比较的问题。

工作流程：

1. 配置 LLM 与语音转写服务。
2. 上传面试录音或粘贴转写文本，并关联职位信息。
3. 提取面试问答与追问链路。
4. 分析考察意图、回答质量与改进方向。
5. 汇总多场面试中的共性弱点与高频考点。

可验证亮点：

- 支持录音和文本输入。
- 支持问答提取与逐题诊断。
- 结合 STAR 或 3W 框架生成改进建议。
- 支持本地数据存储。
- 支持跨面试规律分析。

真实资产：

- 仓库当前没有图片资产。
- 实现阶段运行真实应用并截取上传、逐题复盘和规律分析界面。

#### 案例三：智能简历编辑工具

仓库：<https://github.com/aurostars/Resume-Builder-and-Editor>

背景与目标：减少简历写作、JD 对齐、模板排版和多格式导出的成本，同时优先保护个人数据。

工作流程：

1. 本地配置 AI 服务。
2. 手动创建简历或导入已有简历。
3. 使用 AI 润色、STAR 改写或 JD 优化。
4. 切换模板、颜色和版式并实时预览。
5. 导出 PDF、Word、Markdown 或 JSON。

可验证亮点：

- 多模型接入。
- 本地数据存储。
- 多套模板与主题色。
- 智能分页。
- 多格式导出。

真实资产：

- `public/template-snapshots/zh/modern.png`
- `public/template-snapshots/zh/timeline.png`
- `public/features/polish.png`

来源说明：

- 实现前核对 GitHub fork 和上游信息。
- 如果项目基于开源仓库二次开发，页面必须明确标注上游来源和个人改造内容。
- 不将上游项目的全部功能与成果归为个人原创。

#### 案例四：智能会议纪要工具

仓库：<https://github.com/aurostars/meeting-minutes-extractor>

背景与目标：将原始会议转写转化为可复核、可编辑、可导出的结构化纪要。

工作流程：

1. 输入会议转写与基础信息。
2. 识别说话人并关联姓名与角色。
3. 通过六阶段流程处理话题、要点、决策和待办。
4. 根据置信度高亮进行人工复核和内联编辑。
5. 导出 Word、Excel 或 Markdown。

可验证亮点：

- 六阶段结构化处理流程。
- 说话人识别。
- 决策与待办提取。
- 置信度评估与人工复核。
- 多格式导出。

真实资产：

- 仓库当前没有图片资产。
- 实现阶段运行真实应用并截取输入、处理进度、复核和导出界面。

## 6. 交互与动效

- Hero 内容按阅读顺序轻量进入。
- 案例图片使用滚动触发的遮罩揭示。
- 按钮和链接提供悬停、按下与键盘焦点反馈。
- 所有动画只使用 `transform` 和 `opacity`。
- 不使用 `window.addEventListener("scroll", ...)`。
- 不使用滚动劫持、无限跑马灯或纯装饰动画。
- 所有动效遵守 `prefers-reduced-motion`，降级为静态内容。
- 动效必须服务于阅读顺序、内容层级、交互反馈或状态变化。

## 7. 技术架构

保留现有技术栈：

- Next.js 16 App Router
- React 19
- TypeScript
- Tailwind CSS 4
- GitHub Pages 静态部署

组件边界：

- `Hero`
- `FeaturedCases`
- `CaseStudy`
- `ProjectGallery`
- `WorkflowSteps`
- `ExperienceIndex`
- `EducationAndSkills`
- `Contact`
- 独立的轻量动效组件

案例内容放入类型化数据文件。页面组件只负责渲染，新增项目时不需要重写页面结构。

页面不引入后台、数据库、联系表单或运行时业务数据源。

## 8. 链接与数据规则

- 所有案例链接使用真实 GitHub 地址。
- 可公开运行的项目增加在线体验或 Releases 链接。
- 外部链接在新标签页打开，并使用 `rel="noopener noreferrer"`。
- 同一意图只使用一个 CTA 文案。
- 不展示无法验证的用户数量、效率提升或商业成果。
- 页面使用的数字必须来自仓库、用户材料或真实运行结果。

## 9. 图片与失败降级

- 真实截图统一整理到 `public/projects/<project-name>/`。
- 使用明确宽高和响应式图片，避免布局偏移。
- 图片缺失时显示项目名称与说明，不显示破损图片。
- 构建前验证案例必填字段、图片路径和链接格式。
- 静态页面不设计虚假的 API 加载、空数据或接口错误状态。
- 实现阶段若某个项目无法运行，记录阻断原因，并优先使用仓库现有真实资产。

## 10. SEO 与可访问性

- 保留单页主页 URL，不改变 GitHub Pages 路径。
- 更新页面标题、描述、Open Graph 元数据与社交分享图。
- 添加跳到主内容链接。
- 使用语义化 `nav`、`main`、`section`、`article` 和 `footer`。
- 所有有意义图片提供具体 alt 文本。
- 所有交互可通过键盘完成，并具有可见焦点。
- 正文与控件达到 WCAG AA 对比度。
- 导航桌面端保持单行，高度不超过 80px。

## 11. 测试与验证

实现阶段采用测试优先流程：

1. 先为案例数据结构、链接和核心页面内容编写失败测试。
2. 实现最小代码使测试通过。
3. 再进行组件拆分和样式重构，并保持测试通过。

最终验证包括：

- 单元测试与页面内容测试。
- ESLint。
- TypeScript 检查。
- Next.js 生产构建。
- GitHub Pages 静态资源路径检查。
- 桌面、平板和手机宽度检查。
- 键盘导航与焦点检查。
- `prefers-reduced-motion` 检查。
- Lighthouse 性能、可访问性、最佳实践与 SEO 检查。
- 首屏 LCP、CLS 与交互响应检查。

当前仓库没有 `test` 脚本。实施计划必须先选择并配置与 Next.js 兼容的最小测试方案，再开始生产代码变更。
